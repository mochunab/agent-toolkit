# Mac에서 안드로이드 앱 테스트하기 — ADB 직접 조작

> 목표: AI가 폰의 원본 화면을 읽고 ADB로 한 번씩 조작한 뒤 기대 결과와 대조한다.
> 문서 기준일: 2026-10-04. ADB는 안드로이드 전용이다.

## 1. 연결과 테스트 조건을 준비한다

[안드로이드 연결·미러링 가이드](안드로이드-맥-미러링-가이드.md)로 설치·USB 디버깅·폰 승인을 완료한다. scrcpy는 사람이 함께 볼 때 선택적으로 켠다. ADB 직접 조작은 Mac 창 위치에 의존하지 않는다.

```sh
adb devices -l
export APP_TEST_SERIAL='YOUR_DEVICE_SERIAL'
export APP_TEST_PACKAGE='com.example.app'
export APP_TEST_DIR="$HOME/app-test-output"
mkdir -p "$APP_TEST_DIR"
adb -s "$APP_TEST_SERIAL" shell wm size
adb -s "$APP_TEST_SERIAL" shell pm list packages -3
```

시리얼·패키지는 실제 대상 값으로 로컬에서 바꾼다. `com.example.app`은 예시다. 모든 명령에서 같은 시리얼을 사용한다. 폰 화면을 켜고 잠금을 해제한다.

`pm list packages -3`는 사용자가 설치한 앱 목록이다. 패키지를 모르면 대상 앱을 사람이 연 뒤 다음 출력의 현재 포커스 값을 확인한다. 제조사·OS에 따라 출력 형식이 다를 수 있다.

```sh
adb -s "$APP_TEST_SERIAL" shell dumpsys window
```

테스트 계정·로그인 상태·앱 버전·시나리오·입력값·중단 지점을 미리 정한다. 루팅이나 앱 데이터 초기화는 기본 절차에 필요하지 않다. [ADB 공식 문서](https://developer.android.com/tools/adb)

## 2. 앱을 열고 첫 화면을 저장한다

```sh
adb -s "$APP_TEST_SERIAL" shell monkey -p "$APP_TEST_PACKAGE" -c android.intent.category.LAUNCHER 1
adb -s "$APP_TEST_SERIAL" exec-out screencap -p > "$APP_TEST_DIR/01-before.png"
```

이 `monkey` 명령은 지정 앱의 런처 진입용이다. 무작위 반복 테스트 명령으로 확대하지 않는다. AI에게 생성된 이미지 파일을 읽게 한다. 화면의 앱·로그인·사용자 모드가 예상과 같은지 먼저 확인한다.

**통과 기준:** 캡처 파일이 열리고 현재 폰 화면과 일치한다. 파일이 존재하는 것만으로 성공 처리하지 않는다. 보안 화면의 캡처 제한은 우회하지 않고 BLOCKED로 기록한다.

## 3. 좌표는 원본 이미지 픽셀 기준으로 읽는다

원본 PNG의 왼쪽 위를 `(0, 0)`으로 삼는다. AI 이미지 뷰어가 축소 표시할 수 있으므로 원본 크기와 읽은 좌표의 기준을 확인한다.

| 읽은 근거 | ADB 입력에 쓸 좌표 |
| --- | --- |
| 원본 스크린샷 | 원본 픽셀 |
| 축소 미리보기 | 원본 폭/미리보기 폭, 원본 높이/미리보기 높이로 각각 환산 |
| UI XML의 bounds | 기기 좌표. 원본 스크린샷과 대조 |

예: 원본 폭 1200, 미리보기 폭 600이면 x 좌표를 2배로 환산한다. y도 실제 높이 비율로 환산한다. 회전·크롭·화면 배율이 바뀌면 이전 좌표를 재사용하지 않는다.

## 4. 한 번 조작하고 새 화면을 확인한다

아래 좌표는 **명령 형식 예시**다. 첫 화면에서 실제 버튼·안전한 스크롤 영역을 읽은 값으로 바꾼 뒤 실행한다.

```sh
adb -s "$APP_TEST_SERIAL" shell input tap 100 200
adb -s "$APP_TEST_SERIAL" exec-out screencap -p > "$APP_TEST_DIR/02-after-tap.png"
```

새 이미지를 읽고 기대한 변화가 나타났는지 확인한다. 전환·로딩 중이면 화면을 다시 읽고 안정된 뒤 다음 동작을 정한다.

```sh
adb -s "$APP_TEST_SERIAL" shell input swipe 300 800 300 300 400
adb -s "$APP_TEST_SERIAL" shell input keyevent KEYCODE_BACK
```

위 두 동작도 각각 별도로 실행하고 중간 결과를 확인한다. 연속 탭·스와이프를 묶어 보내면 알림·화면 전환에 의해 엉뚱한 위치를 누를 수 있다.

## 5. 화면 글자·요소 정보를 보조로 읽는다

```sh
adb -s "$APP_TEST_SERIAL" shell uiautomator dump /sdcard/app-test-ui.xml
adb -s "$APP_TEST_SERIAL" exec-out cat /sdcard/app-test-ui.xml > "$APP_TEST_DIR/ui.xml"
```

AI가 XML의 `text`, `content-desc`, `resource-id`, `bounds`와 화면을 대조한다. bounds의 사각형 중심은 누를 위치의 후보이며, 실제 화면에서 확인한 뒤 사용한다.

요소가 적거나 비어 있다는 사실만으로 웹뷰라고 확정하지 않는다. 웹뷰·커스텀 렌더링·접근성 정보 부족 등 원인이 있다. 스크린샷으로 점검하고 내부 상태는 확인되지 않았다고 기록한다.

## 6. 문자 입력·긴 목록을 처리한다

ASCII 입력 예시 — 입력창이 선택됐는지 먼저 확인한다.

```sh
adb -s "$APP_TEST_SERIAL" shell input text 'test'
```

한글 등 Unicode를 위 명령으로 안정적으로 입력한다고 가정하지 않는다. 추천 검색어·자동완성 선택, 사용자의 초기 입력, 현재 키보드 화면을 확인한 개별 탭 중 적합한 경로를 선택한다. 다른 기기의 키보드 좌표를 그대로 쓰지 않는다.

긴 목록은 항목 이름 검색을 우선 사용한다. 스크롤 수집은 횟수·시간 제한과 종료 조건을 정하고, 중복 항목·아직 로딩 중인 상태를 구분한다. 새 항목이 잠시 없다는 것만으로 목록 끝을 확정하지 않는다.

## 7. 테스트 한 사이클

1. [결과 기록 템플릿](테스트_시나리오_결과_기록_템플릿.md)에 입력값·기대 결과를 먼저 적는다.
2. 첫 화면을 읽고 앱·모드·로그인·초기 상태를 확인한다.
3. 한 번 조작 → 새 화면 읽기 → 기대 결과 대조를 반복한다.
4. PASS / FAIL / BLOCKED와 증거 경로를 기록한다.
5. 숫자·건수는 근거 목록과 재계산한다. 해석과 실제 관찰을 나눠 적는다.
6. 다음 테스트에서 재현할 초기화 방법을 기록한다. 임의로 앱 데이터를 지우지 않는다.

조회 점검이라면 요청·결제·메시지 발송 직전에서 멈춘다. 해당 동작을 테스트해야 한다면 전용 환경·계정·승인된 시나리오를 먼저 마련한다.

## 8. 문제 해결과 다음 단계

| 증상 | 확인·조치 |
| --- | --- |
| 기기 없음 / unauthorized | 케이블·디버깅·폰 승인 확인 |
| 탭 위치가 다름 | 원본 픽셀·축소 비율·회전·화면 전환 확인 |
| 캡처가 검음 | 대상 앱의 보안 화면인지 확인, 판정은 BLOCKED |
| 한글 입력 실패 | 입력 방법·키보드 상태 재선택 |
| 예상과 다른 앱·모드 | 입력 중단, 새 화면부터 확인 |
| 로딩이 끝나지 않음 | 시나리오의 대기 한도 이후 BLOCKED/FAIL로 기록 |
| UI XML 정보가 부족 | 화면 기반 점검으로 전환, 원인 단정 금지 |

필요한 경우 대상 앱만 종료할 수 있다. 다음 명령은 화면 상태를 바꾸므로 진행 중 데이터가 있는지 먼저 확인한다.

```sh
adb -s "$APP_TEST_SERIAL" shell am force-stop "$APP_TEST_PACKAGE"
```

스크린샷·UI XML·로그에는 개인정보가 들어갈 수 있다. 공유용 증거는 불필요한 화면을 제외하고 이름·연락처·인증정보를 가린 뒤 다시 열어 확인한다. 파일명과 기록에도 계정·기기 식별자를 넣지 않는다.

이 방법은 화면 기반 탐색·QA에 적합하다. 안정적인 반복 회귀에는 [Appium](https://appium.io/docs/en/latest/) 같은 도구와 별도 단언·초기화·대기 설계가 필요하다.
