# 프로젝트 CI 적용

[`security-deploy.yml`](../assets/security-deploy.yml)은 npm 프로젝트용 검토 템플릿이다. 공유 스킬 폴더에 보관하며 자동 활성화하지 않는다. 프로젝트의 기존 CI·패키지 매니저·배포 방식을 먼저 확인하고 필요한 job만 병합한다. pnpm/yarn/다른 언어에는 그대로 복사하지 않는다.

## 프로젝트 적용 실행 절차

"프로젝트에 보안 연결해줘", "이 프로젝트 보안 검사 자동으로 해줘", "배포 전에 보안 검사하게 해줘", "보안 문제 있으면 배포 막아줘", "이 프로젝트 CI에 보안 검사 연결해줘"처럼 설정을 요청하면 다음 절차로 실제 작업한다. CI라는 용어를 입력하게 요구하지 않는다. 시작할 때 자동 보안 검사와 검사 실패 시 배포 차단을 연결한다는 범위를 쉬운 말로 알린다.

"보안 점검만", "CI 보안 상태만 확인", "프로젝트에 보안 연결돼 있는지만 확인해줘"는 [읽기 전용 점검](review-workflow.md)으로 처리한다.

1. **대상 확정**: 명시 경로/저장소 또는 대화에서 확정된 현재 프로젝트를 사용한다. 대상이 없으면 필요한 정보만 확인한다. 프로젝트 AGENTS/CLAUDE/README, Git 상태, 기존 미커밋 변경을 읽고 보존한다.
2. **배포 경로 조사**: 패키지·잠금 파일·기존 검사와 테스트, `.github/workflows` 등 CI, production 브랜치, 실제 호스팅 Git 자동 배포/Deploy Hook/CLI 경로를 확인한다. 읽기 권한이 없는 외부 설정은 미검증으로 기록한다. 여러 배포 workflow가 있으면 모두 조사한다.
3. **적용안 구체화**: 프로젝트에 필요한 검사, 재사용할 기존 도구/테스트, 새 도구 후보, 변경 파일, 연결할 required check와 호스팅 설정을 정한다. 외부 스캐너·규칙은 이유·대안·영향과 기존 승인 여부를 확인한다. 이미 승인된 선택을 다시 묻지 않는다. 설치/외부 설정 변경의 권한이 부족하면 나머지 로컬 적용안을 검토 가능한 상태로 준비한 뒤 필요한 권한만 요청한다.
4. **로컬 CI 구현**: 승인된 범위의 프로젝트 파일을 수정한다. 기존 검사/배포 workflow에 우선 병합하고, 아래 계약에 맞는 스캐너 실행·실패 전파·보안 회귀 테스트를 구현한다. 프로젝트 언어/매니저와 다른 템플릿을 그대로 복사하지 않는다. 도구·규칙 버전 고정, 전체 Git 히스토리, 시크릿 마스킹, 동일 SHA, PR의 production 시크릿 격리를 유지한다. 필수 검사가 준비되지 않았으면 production 활성화 상태로 만들지 않는다.
5. **로컬 검증**: 프로젝트가 정한 허용 환경에서 명령·설정 문법·관련 테스트와 실패 전파를 검증한다. 새 도구 미설치나 외부 환경 부족으로 실행 못 한 항목은 명시한다. mock/local 테스트는 CI 실제 run 증거를 대체하지 않는다.
6. **원격 연결**: 현재 세션에서 승인된 대상/권한 범위에 따라 커밋·푸시·검증용 CI 실행·required check·호스팅 경로 연결을 진행한다. 로컬 CI 구현 요청만으로 production 배포를 실행하지 않는다. 아직 권한이 없는 외부 변경은 정확한 diff·설정 값·영향을 제시한 뒤 필요한 최종 승인을 요청한다. 이미 승인된 작업의 권한은 재요청하지 않는다.
7. **강제 차단 검증 및 보고**: 아래 성공/실패 대비 테스트와 우회 경로 검증을 완료한다. 작성한 파일, 로컬 검증, CI 실제 run, required check, 외부 배포 경로 상태를 각각 보고한다. 미완료가 있으면 해소 조건을 남기고 전체 완료로 보고하지 않는다. 실제 production 배포는 사용자의 배포 요청에 따라 별도의 `security-review → deploy-checker` 게이트를 거친다.

## 적용 전 계약

- `.nvmrc`와 npm 잠금 파일을 프로젝트 버전에 맞춘다. 다른 Node 설정 파일을 쓰면 `node-version-file`을 바꾼다.
- 외부 스캐너/규칙 추가는 이유·대안·영향과 승인을 확인한다. 현재 템플릿은 스캐너를 자동 설치하지 않는다. 선택된 도구·규칙을 검토하고 버전/SHA 또는 검증된 배포물 해시를 고정해 설치 단계를 추가한다.
- lifecycle scripts는 기본 실행하지 않는다. codegen/빌드 준비가 필요하면 검토한 특정 명령만 추가한다. PR job에 production 시크릿을 주지 않는다.
- 의존성 예외는 [배포 게이트의 의존성 예외](deployment-gate.md#의존성-예외) 기준으로 `security/dependency-exceptions.json`에 기록한다. 예외 파일·감사 스크립트 변경은 PR 검토 대상이며, 런타임 패키지를 예외 처리하지 않는다.
- 다음 프로젝트 명령이 없거나 실행되지 않으면 검사는 실패해야 한다. 빈 스크립트나 무조건 성공하는 대체 명령으로 채우지 않는다.

| npm script | 필수 구현 |
|---|---|
| `security:deps` | 의존성 HIGH/CRITICAL 검사. 승인된 빌드·개발 전용 예외만 제외. npm은 [`dependency-audit-gate.mjs`](../assets/dependency-audit-gate.mjs)를 프로젝트(예: `scripts/security/`)에 복사해 연결. 미승인·만료·무효 예외, 감사 실행 실패 시 비정상 종료 |
| `security:secrets` | 승인된 스캐너로 full Git history와 현재 배포 파일 검사. 원문 시크릿 마스킹. 탐지/실행 실패 시 비정상 종료 |
| `security:sast` | 검토·고정된 보안 규칙으로 대상 언어 분석. 차단 발견/실행 실패 시 비정상 종료 |
| `security:tests` | 격리된 테스트 DB/사용자 A·B·비인증/일반·관리 권한, 입력 및 CSRF 등의 실제 허용·거부 테스트. 필요한 테스트가 skip되면 실패 |
| `security:headers` | 해당 커밋이 실행되는 staging URL의 헤더·HTTPS/TLS·CORS 검사. `SECURITY_TEST_BASE_URL` 미설정이나 다른 커밋이면 실패. localhost HTTP는 TLS 증거로 인정하지 않음 |
| `deploy:production` | 해당 체크아웃의 코드를 배포하는 기존 프로젝트 파이프라인. 최신 브랜치를 다시 pull하지 않음. 필요한 자격증명은 production environment에 제한하고 도구 출력에서 숨김 |

플랫폼별 배포 자격증명/OIDC 설정은 대상 프로젝트에서 연결해야 한다. 템플릿에는 자격증명이 없으며 `SECURITY_DEPLOY_ENABLED`가 정확히 `true`일 때만 main push의 배포 job이 실행된다. 이 변수는 아래 차단 검증 완료 후에만 켠다. `workflow_dispatch`는 검사 전용이다.

staging이 없는 프로젝트는 먼저 승인된 격리 검증 환경을 연결한다. 이번 커밋과 무관한 기존 URL의 성공 결과를 재사용하지 않는다. 정적/기능 미사용 항목은 검토된 프로젝트 정책에서 N/A 근거를 명시한다.

## 강제 차단 검증

1. 테스트 PR에서 각 필수 검사 실패·실행 오류를 재현하고 `security-gate` 실패를 확인한다. live 시크릿은 사용하지 않는다.
2. 별도 테스트 환경의 실제 workflow run에서, 검사 성공 시 실행되고 실패·생략·취소 시 실행되지 않는 배포 job을 확인한다. 이벤트·브랜치·enable 조건은 양쪽 run에서 실행 가능한 동일 조건으로 맞추고 테스트 환경의 자격증명만 사용한다. PR 이벤트/enable=false 때문에 원래 skip된 job을 `needs` 차단 증거로 인정하지 않는다.
3. 보호 브랜치의 required check에 `security-gate`를 등록한다. job 이름·PR 이벤트·skip 조건을 대조한다.
4. Vercel Git 자동 배포 등 독립적인 production 경로를 해제/연결하고, CLI·다른 workflow·Deploy Hook 등 우회 경로의 권한을 확인한다. 외부 설정 변경은 실제 대상·영향을 제시한 승인 범위에서 수행한다.
5. 검사 SHA·빌드/배포 코드·호스팅 환경이 일치하는 성공 run을 확인한다. 동일 SHA에서도 외부 DB 정책·환경변수가 변경됐다면 관련 검증을 다시 실행한다.

보고는 템플릿 작성, 프로젝트 적용, CI 실제 실행, required check 등록, 우회 경로 차단을 구분한다. 모든 항목 증거가 있어야 CI 강제 배포 차단 완료다.
